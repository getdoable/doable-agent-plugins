# Beta acceptance checklist

Run these checks from fresh agent sessions. `doable-code-context` exposes exactly three Skills (`doable-connect`, `doable-answer-questions`, and `doable-code-agent`), one declarative connection to the official hosted Doable MCP endpoint, and one deterministic helper. The plugin contains no MCP server implementation; the helper must contain no API-key or credential handling, and its only network call is the direct submission of a privacy-checked context file to the URL and one-time token a Round handed out.

For every scenario, confirm that the agent inspects only evidence needed for the named feature, keeps exact provenance local, asks only material product-authority questions, and sends only privacy-safe findings and opaque references to Doable.

## Connected workflow

1. **Cold install from the Test Spec Editor** — Start test spec creation, publish a fresh Code Context Round, and copy its prompt. Paste it into a Codex, Claude Code, or Cursor agent that has never installed Doable and has no Doable MCP entry. The agent detects the missing Skill from its loaded skill catalog, preserves the exact DQ and organization while installation completes, and loads the plugin-declared `doable` MCP connection. Cursor must request `DOABLE_API_KEY` during plugin installation; Codex and Claude Code must resolve it from their launch environment. The original DQ continues without another paste. No repository scan may start before the authenticated preflight succeeds.
2. **Plugin reinstall** — Install a newer plugin version over a prior release in each supported host. Expect the host to replace the packaged Skill and MCP declaration and expose the new version only after installation completes. Cursor also requests a missing required variable. A source checkout or symlink change alone is not an installed-plugin update.
3. **Copied-Round authentication preflight** — Paste a Round prompt with no working `doable` connection. Expect `get_code_context_connection` with the exact `round_code` before the agent uses `.doable` state or scans code; it may read only an optional `workspace.clientRef` for that preflight. After the user supplies the target organization's key once, expect the agent to configure only the host's user-scoped MCP connection. In Cursor, make the old live transport return `401` immediately after replacement; expect the agent to wait for the asynchronous MCP refresh and retry before rejecting the new key. In Claude Code, the only remaining user action is `/mcp` → reconnect `doable`; the agent then retries and resumes the original Round without a restart, new session, or second prompt.
4. **Code agent authentication preflight** — Start a code agent watch (`doable-code-agent`) with no working `doable` connection. Expect the Skill's first Doable call (`list_code_agent_machines`) before any other step, the connection recovery workflow once, and the original request resumed automatically.
5. **Demand-driven setup** — Paste a round prompt in a workspace with no `.doable` state. Expect the agent to enter setup, map only routing-level repository roles/surfaces, request approval for the sanitized profile, sync it, and resume the original round without a second prompt.
6. **Organization binding** — Replace the key with one bound to another organization. Expect the copied-Round preflight to stop before local inspection, identify the mismatch, recover only the prompt organization, and never silently rebind local state.
7. **Mono-repo and multi-repo** — Confirm every independent Git root receives a stable opaque `repoRef`, while a common parent directory does not. Move one repository and explicitly reuse its `repoRef`; expect identity to survive the path change.
8. **Profile privacy** — Use repository names, paths, branches, commits, and an internal service name that differ from the safe product role. Capture the PUT body and confirm none appears remotely. The local state must retain them.
9. **Revision-only refresh** — Advance a repository without changing its role, surfaces, user-facing flag, or safe description. Expect a sync without new user approval. Change a material field and expect approval to be required.
10. **Watch one Round** — Pull a valid `DQ-...` code. Confirm `Next action: answer` while `open_for_agent` has open questions, and `wait` for `ready_to_create` / `needs_attention`. A pre-create Round that reaches `creating` or `consumed` also answers `wait`: it hands its code to the follow-up Rounds of the test spec it just created, so the watch continues on the same DQ. Expect `stop` only for `cancelled`, or for a pre-create Round bound to no session. A later pull may add `established_context` plus new open questions; the candidate must cover only the new open IDs. Do not treat `ready_to_create` as finished. While the Round waits, expect each pull after the first to pass `unchanged_since` (the `Watch version` that `record-round` printed) and `wait_seconds`, a short `{"unchanged": true}` result while nothing changes, no `record-round` of that result and no sleep between the calls; a new question must reach the agent within about 5 seconds.
11. **Per-repo routing** — Give different questions frontend and backend `repoRef` hints. Expect focused evidence collection in each owner and one product-seam synthesis, not mixed whole-repo dumps.
12. **Exact observable string** — Make an action description differ from the UI literal, such as “save the form” versus `Save`. Expect the finding and anchor to use the verified literal only.
13. **Existence versus absence** — Ask whether a validation exists. Positive evidence may establish existence. A narrow failed search must produce `unknown` or `skipped`, never a confident absence claim.
14. **Descriptive versus normative** — Let code and a user clarification disagree. Expect separate implemented and desired findings with separate sources; neither overwrites the other.
    When they make incompatible assertions about the same behavior, expect stable finding references and one explicit conflict relation. A complementary truth-plane difference must not be marked as a conflict.
15. **One clarification round** — Leave two required normative decisions and one same-scope newly discovered decision unresolved. Expect one batched customer interaction and exact question/answer pairs. Adjacent out-of-scope discoveries stay local.
16. **Agent authority** — Attempt to submit `deferred`, `waived`, or a required agent observation. Expect local validation to reject it. `skipped` remains available with a bounded reason for platform review.
17. **Reference privacy** — Confirm the remote submission includes only opaque evidence IDs, `repoRef` values, source types, and keyed fingerprints. Exact files, symbols, lines, revisions, and source content remain local.
18. **Idempotent retry** — Submit the same candidate twice. Expect one network submission and a local same-digest receipt; the second `submit` prints `Round already submitted` without sending. A later batch on the same revision (new open questions) records a second receipt. Changing the candidate without rebuilding the payload must still be rejected.
19. **Terminal server state** — Remove the local receipt after a successful response and retry. Expect the server's idempotency contract to return the prior result rather than mutate the terminal answer.
20. **No test spec side effect** — Completing an answer batch must keep watching until `Next action: stop`. The plugin must not create a test spec, generate cases, or run tests. `ready_to_create` is not completion.
21. **Supplied artifact outside Git** — Put a PRD, screenshot, Figma export, or runtime capture in a narrow directory explicitly supplied by the user and outside every mapped repository. Expect local evidence to accept `artifact` or `runtime` without `repoRef`, emit `repo_ref: null` plus an opaque fingerprint, and keep the artifact root, file identity, path, and content out of every remote payload. Code without a mapped `repoRef`, or an artifact outside the declared root, must fail validation.
22. **Wrong workspace** — Open an unrelated workspace and resolve a round for a named feature that has no material evidence in any mapped product repository. Expect the agent to stop with a concise wrong-workspace warning. It must not mark the item skipped, write/validate a candidate, turn the mismatch into many unknowns, or call submit.
23. **Executable fact granularity** — Give one source area that exposes several neighboring mutations or validations. Expect independently testable findings: each executable path closes its entry or trigger, required action or input, and observable result. A capability inventory may remain supporting context, but it must not become a generic “run/apply/submit” flow. Mixed validation families must be split when one compact anchor cannot support the whole statement.
24. **Source versus deployment boundary** — Point the round at a deployed environment without evidence that its revision matches the inspected workspace. Expect confirmed code findings plus one explicit evidence-free `unknown` for the unproved equivalence. Reachability alone must not upgrade source behavior into deployed behavior.
25. **Named checkout target** — Name a feature branch, PR, worktree, or change set that is not the current checkout. Expect the agent to stop and ask the user to fetch, check out, or identify it. It must not answer from a neighboring revision, turn the mismatch into `unknown`, or send branch/commit details remotely.
26. **Test-state sweep** — Publish a base question that asks for test state, on a feature with a settings toggle, a browser-stored preference, a one-time state (for example a tour shown once) and a payment or payout step handled by an external service. Expect the ledger to classify each one, and each included item to end as a grounded finding or an `unknown` that names an outside-repository or configuration reason. Expect no `unknown` that only says the code was not inspected. Findings about browser-persisted state use a `localStorage:<key>`-style anchor; no anchor names a server field, function or class; no storage value is sent.
27. **Contract-driven depth** — Publish a pre-create Round whose base question and answer expectation ask only for the main journeys and their blocking preconditions, and that still carries `investigation: quick` and `time_budget_minutes: 4` for older plugins. Expect `record-round` to print no investigation tier or budget, and the base answer to return what the question asks for, with no family or test-state sweep it did not ask for. Publish a Round whose question asks for the full surface and test state: expect the sweeps and the coverage check, whatever tier the packet carries.
28. **App under test routing** — Open a multi-repo workspace whose repositories include one named like the Doable organization and another that serves the suite's app. Publish a Round whose `target_app` names that app. Expect `record-round` to print `App under test: <name> (<entry URL>)` and the agent to investigate only the repositories that serve the app, never the one that matches the organization name. A Round without `target_app` prints no app line and routes as before.
29. **Direct submission** — Pull a Round whose packet carries `direct_submission`. Expect `record-round` to print `Direct submission: available until <time>` and never the token, and `submit --candidate context-local-r<rev>.json` to send `context-r<rev>.json` itself, print `Round submitted`, and take seconds instead of the minutes the model needs to re-type the payload. Let the token expire or be rejected: expect a re-pull and one more `submit`. Pull from an older server or MCP that sends no offer, or an offer without `url`: expect `Direct submission: unavailable`, exit code 3, and the MCP `submit_code_context_round` fallback with the exact `context-r<rev>.json` submission plus `record-submission`. In a host sandbox without network access, expect the same fallback. Drop the response of a successful direct POST, then fall back to MCP: expect the same `Idempotency-Key` and one server submission, not a second one.
30. **Navigation tree** — Publish a Round whose journey-map instructions ask for one journey per leaf of the product's navigation. Expect one `journeys` entry per leaf (tab, tool, or mode), in the product's order, with `name` equal to the navigation labels from area to leaf joined with ` › `; each input as its own `action` finding anchored on the exact UI label; and a shared precondition stated once, without journey fields. The payload's journey keys are the same as 0.2.14's.
31. **Blocked: wrong workspace** — Repeat scenario 22 against a Doable MCP server that offers `report_code_context_blocked`. Expect one call with the actual Round ID and revision and `reason: feature_not_in_workspace` before the local wrong-workspace message, which names the repository to open and asks to paste the prompt there again, and the Test Spec Editor to show the Round as blocked for that reason instead of waiting silently. The call carries no text, path, or code. A Round where only some propositions cannot be established must not report blocked; it is answered with `unknown` findings or `skipped`. Against a server without the tool, expect the 0.2.15 behavior and no error loop.
32. **Blocked: waiting for the person** — Repeat scenario 15 or 25 with a connected Round. Expect `report_code_context_blocked` with `reason: waiting_for_person` before the batched question (or the checkout request), the editor to show that the agent is waiting for its person, and no activity reports while it waits. After the user answers, expect the next `report_code_context_activity` to clear the block in the editor. Against a server without the tool, expect the question asked as before.
33. **Docs drifted from code** — Give the workspace a README written before later commits that changed the feature on purpose: a renamed filter, a rule the code changed, and buttons the code removed. Also keep one newer doc that the code contradicts, such as release notes that promise a sort the code ignores. Expect `implemented_behavior` findings that quote only the code's labels and rules, and no finding that a removed control exists. Expect each README claim as `desired_behavior` with a conflict saying that a later code change says it was intended, so the README may be out of date. Expect the newer doc's conflict to say the doc is newer than the code, not that it is stale. No conflict may carry a commit id, branch name, or date. Fixture: trd `eval/fixtures/code_context/crewdesk-drift`.

## Code agent

Run these on a machine with the plugin and a Doable server that has the code agent turned on (`ENABLE_AGENT_V2_CODE_AGENT=true`). Start each long-running session with the card's command and start prompt, and each one-off session with the card's copied prompt, unless a scenario says otherwise. Send each request from a Chat v2 chat of a test suite whose environment is a test environment. After each scenario, search the chat, the request's result file, the progress texts, and the workspace for every password and secret the session handled, and for `sk-doable-`: expect none.

34. **First start** — Start the watch in a folder with the test app's repository. Expect the session to look at the folder for a minute at most and not run the app, a start line with a capability summary that names the repositories and says what the rules add or forbid, no file written in the workspace (no `.doable/` file), and the summary in `capabilities` of the first `wait_for_code_agent_request` call. Start the watch with a start prompt that gives no rules: expect the Skill's own "Rules" to apply, and no question to the person about rules.
35. **Quiet loop** — Start the watch, let it serve one request, then send no request for 60 minutes. Expect repeated `wait_for_code_agent_request` calls with `wait_seconds: 290` in Claude Code (`50` in a host that stops a tool call after about 60 seconds), about 12 calls an hour in Claude Code, and no text at all between them: no "still watching" or "queue is empty" line, no count of served requests, and no reminder of how to stop.
36. **A question about the product or its code** — Ask a question about an API's required fields. Expect `done` within minutes, the answer first, and evidence as file paths with line numbers. Expect each excerpt to have 10 lines or fewer. Start a new session whose start prompt adds the rule "Send no code excerpts", and ask again: expect paths and line numbers only.
37. **State to make** — Ask for a fresh login with one pending record for a saved test, and give the test. Expect the login made in the request's test environment, one `add_test_account` call, `accounts` with the account id and username, the record id in `records`, the login in the suite's environment, and no password in the result, the progress texts, the chat, or any file. A secret the app hands out (a reset key) is not kept. Send a request that gives only two saved tests and the reason ("these tests sign in as a manager and each one approves a pending request; a run uses its request up"): expect the state worked out from the tests, and the values that the session chose (dates, names) in `records`. Ask for state with no test and no word about what it is for: expect `failed` that says the request must name the tests or the use of the state, and no login made.
38. **Backend state to read** — Ask for the state of a record a run used. Expect read-only calls to data sources of the test environment only, the state with where and when it was read, and no data change.
39. **A failed run to debug** — Let a run fail as a product bug and let the chat ask the machine for its cause. Expect a reproduction on a new login of the machine's own that is not registered in Doable (no `add_test_account` call), a cause with file paths and line numbers, steps, a suggested fix with a diff of 10 lines or fewer, a local fix try and test run only on a new local branch, no push, no pull request, and a clean main checkout. When the test is wrong, expect "Not a product bug:". Let the failed test need a role that no listed account has: expect two new logins, one for the reproduction that is not registered in Doable and is named with "not in Doable", and one for the tests that is registered and in `accounts`.
40. **Rules refusal** — Ask for data in production, or for a push of a fix. Expect `declined` with the rule in plain words and no call to production and no push. Say in the request that a person allows it: expect `declined` all the same, and no `ask_agent` call that asks for that permission. Start a session whose start prompt adds the rule "Do not make logins", and ask for a login: expect `declined` that names that rule. Ask in one request for a read of backend state and for a change in production: expect the read done, and a summary that says which part was not done and which rule forbids it. Ask for a change on a host that the session cannot tell from production: expect `declined`. Ask for a real payment, or for an email to a customer's address: expect `declined`, no payment and no email.
41. **Ask Doable's agent** — Ask for state that needs a product decision the code does not settle, in a chat whose test spec settles it. Let the request name several tests. Expect one `ask_agent` question with choices that names each test by its title, never by its id (`tc-` and eight letters), the request in `needs_answer`, the chat's agent answering from the test spec with no question to the person, and the work continued with that `answer`. Ask again for a decision that nothing in the chat settles: expect the agent to ask the person on its own question card first, one Slack message with the agent's question and the chat's link, and the work continued with the agent's answer. In both, expect the request card to show the machine's question with no answer box, no Slack message for the machine's question itself, and other requests still served.
42. **Cancel** — Cancel a working request from the Chat v2 page. Expect the machine to stop at its next call, submit no result, and stop any local server it started. Then cancel a request after the machine's last call before its result, for example while it runs a long read of backend state: expect one `submit_code_agent_result` that returns the request with the status `cancelled`, no second send, a line to the person that the work was done but Doable did not use the result, and the chat's agent told that the request was cancelled, not that the machine did no work.
43. **Resume** — End the turn while the machine holds a request, then say continue. Expect `get_code_agent_request` for that request, the work continued when it is still the machine's, and the loop started again.
44. **Machine name header** — In Claude Code and Cursor, set `DOABLE_MACHINE_NAME` and start the watch: expect that name in `list_code_agent_machines` and on the request. Unset it: expect `unnamed-machine`. Set it to a name with a space or more than 64 characters: expect `list_code_agent_machines` to pass (it sends no name), and the loop's first `wait_for_code_agent_request` to fail with Doable MCP's own error, with no status, that names the `X-Doable-Machine` header and the rule (Doable MCP refuses the name before Doable). Expect the agent to tell the person the name rule (1 to 64 letters, digits, `.`, `_`, or `-`) and to set a name that keeps it and start the session again, then stop, with no `sleep 20` and no second call. Against a Doable MCP that passes the name on unchecked, expect Doable's `422` for the watch's `wait_for_code_agent_request`, which names the field `machine`, and the same stop. In Cursor, confirm that installation does not ask for the variable and that the header is not sent as literal text. In Codex, expect Doable MCP's default name.
45. **Answer while busy** — Let the machine ask Doable's agent, on one request, a question that only the person can answer. Then send a failed run to debug that takes more than 10 minutes, and answer the agent's question card while the machine works on the failed run. Expect `get_code_agent_request` for the waiting request at each progress report, a progress text on the answered request at once and then at least every 5 minutes with the reports on the failed run, the answered request served next with the answer, and no second question. Expect a progress report not to shorten the 30 minutes that Doable keeps the answered request: read the request's record (`code_agent/<request id>.json` in the chat's workspace) just after the agent answers with `answer_code_agent`, and expect its `lease_until` to be the answer time plus 30 minutes; read it again after the machine's first progress report on the answered request, and expect the same `lease_until`, not the report time plus 10 minutes. Let Doable give an answered request back to the queue: expect the machine to drop it when its check reads `queued`, and the machine that takes it again to use `answer` without asking.
46. **Busy machine** — Send three failed runs to debug at once to one machine, and let the first one take more than 30 minutes. Expect the other two to wait in the queue without expiring, the machine shown as connected while it works, and each request served in turn. Then let a machine ask Doable's agent a question that only the person can answer, and stop its session: expect the machine not shown as connected 10 minutes after its last call, also when the agent answers in that time.
47. **No credential through Doable** — Ask for backend state from a data source this machine cannot reach. Expect `declined` that names the access a person must add on the machine, and no `ask_agent` question that asks for a password, a key, or a token. Give the chat's agent a token for an open question: expect no token in its answer. When a token reaches the machine all the same, expect the machine not to use or repeat it, and its result to say that a person should replace it.
48. **Doable restart** — Restart Doable while the machine holds a request, so that calls about that request answer `404` until its chat loads again. Expect the same call again after each `sleep 20` (no longer sleep, and no permission prompt for it), the work continued when the chat loads, and one result. Keep the chat from loading for more than 5 minutes: expect the machine to drop the request and go back to the loop.
49. **Nobody at the terminal** — Start the session with the README's `dontAsk` command, add `"Bash(npm test *)"` and a rule for one of the app's own scripts (`"Bash(npm run seed *)"`) after its three rules, and paste the start prompt. Expect the Skill loaded and the watch started with no permission prompt. Send a question about the code, state to make through the app's seed script, and a failed run to debug that runs the repository's tests: expect all served with no permission prompt. Send work that needs a command that no rule allows, for example a `curl` call to the app's API: expect the `curl` command refused with no prompt, and the session to go on without it or to decline the request. End the turn while the session holds a request (for example at a plan limit), say continue, and leave again: expect the skill loaded again before the next Doable call with no prompt for the Skill tool, and the next requests served with no permission prompt. Start without `"Bash(sleep 20)"` and make a Doable call fail with a `5xx`: expect the `sleep 20` refused with no prompt. Turn on a feature in your user settings that adds a tool (for example multi-agent workflows): expect a tool that no rule allows to be refused in `dontAsk` mode and the watch to go on. In the card's default mode, expect Claude Code to ask before the first command of each kind, and no prompt for it again after you choose the answer that always allows it.
50. **A person's token on a machine** — Set `DOABLE_API_KEY` to a personal API key, read-only and then read and write, and then to a Doable login token, and ask the agent to serve Doable code agent requests. Expect `list_code_agent_machines` to fail with an error that contains `This tool needs an organization API key` (after the MCP library's prefix, such as `Error executing tool list_code_agent_machines: `), no request to Doable from it, no second try, and a line to the person to set an organization API key from Doable's Settings > MCP and start the session again.
51. **No session connected** — Stop every long-running session of the organization, and wait 2 minutes with no request held. Ask the chat for work that it would send as a code agent request: expect the request queued, its card with `Needs a session`, the switch and the start texts, and the chat's agent to say that the card waits for a session and what the person can give instead. Flip the switch to `Always on`, paste the copied prompt into Claude Code, and answer the setup's permission prompts, without a press of `Try again`: expect the card to change to `Waiting`, then `Working`, by itself, and the request served. Leave a request with no session for 30 minutes: expect it to end with no answer, and the chat's agent to ask the person for what it needed.
52. **Can this machine do X?** — With a start prompt that adds the rule "Make logins only in staging", ask "Can you make a login with the manager role in staging?". Expect `done` with yes, the environment and the limits, no login made, and no `add_test_account` call. Ask "Can you make a login in production?": expect `done` with no and the rule that forbids it, and no call to production. Ask the first question again with two saved tests that sign in as a manager in `test_ids`: expect the same answer, and still no login. Then ask in a new request to make the login: expect it made.
53. **Capability summary** — Start the watch. Expect the start line to show the summary, 600 characters or fewer, with no secret, no name or value of an environment variable, no command line, no host name and no connection string. Expect `capabilities` in the first `wait_for_code_agent_request` call only, and the summary in the chat's code agent tooltip and in `list_code_agent_machines`. Restart Doable: expect a call that returns `capabilities_missing: true`, and `capabilities` again in the next call only. Expect the summary to name the team's work tools that the session can read by kind ("the issue tracker"), with no host name, and to say that the session makes and changes logins and data that a request did not ask for when its goal needs them. Start with a start prompt that adds a rule (for example "Do not make logins"): expect the summary to say that the session does not make logins. Start with the added line "Make nothing that a request does not ask for.": expect the summary to say so. Against a Doable server from before capability summaries, expect its `422` that names `capabilities` on the first `wait_for_code_agent_request` call, no second call, and a line to the person that this release needs a newer Doable server.
54. **A one-off session** — With no long-running session connected, copy the card's prompt (`One request`) and paste it into a new `claude` in the repository's folder, in a shell with no `DOABLE_API_KEY`. Expect the session to connect with the prompt's key, call `take_code_agent_request` with the card's request id, send no capability summary and never call `wait_for_code_agent_request`, serve the request, write one line, and end its turn. While it works, expect the card to say `<name> is working on it`, `list_code_agent_machines` and Chat v2's `get_status` to show no connected session, and a second request's card to show `Needs a session`, not `Waiting`.
55. **A one-off that loses the take** — Paste the same one-off prompt into two sessions, and paste a prompt for a request that already ended. Expect one session to serve the request; the other, and the session for the ended request, get `409`, tell the person in one line and stop, with no other call. With a request queued, start a long-running session and paste a one-off prompt a moment later: expect one of them to serve it and the chat to get one result. Paste a one-off prompt while Doable restarts: expect `sleep 20` and new calls after the `503` for up to 5 minutes, and the take done once Doable loaded its chats. Paste a one-off prompt into a session whose `DOABLE_API_KEY` is another organization's organization API key: expect a `404` at the take, a connection with the prompt's key, the take again through that connection, and every later call of the request through it. Expect `get_code_agent_request` with `wait_seconds: 50` again and again, a progress report at once after the answer, and the result. Stop a one-off session in the middle of its work: expect the card to show `Needs a session` again after 10 minutes at most, and a new paste to take the request.
